Ratewise

AI-powered rate intelligence for the creator economy

Most creator pricing tools are either opaque black boxes or static spreadsheets that cannot adapt to platform, engagement, or geography. Ratewise builds pricing from first principles with 12 visible multipliers. The result is a defensible price range both creators and brands can trust.

Engineering Proof

Deterministic Pricing Engine vs Black-Box AI

The project ships both a deterministic algorithm and an OpenAI fallback. The decision to build the algorithm was intentional: financial decisions require auditable math, not opaque LLM outputs. The function below composes 12 multipliers into a single transparent price. Every factor is inspectable, testable, and explainable.

src/lib/utils/pricing-calculator.ts Lines 374–476 
export function calculatePrice(options: CalculatePriceOptions): PricingBreakdown {
  const { platform, followers, contentType, deliverables, engagementRate,
    industry, geography, campaignDuration, usageRights, exclusivity,
    rushJob, revisions, currency = 'USD' } = options;

  const tier = getTier(followers);
  const basePrice = BASE_RATES[tier];

  const effectiveEngagementRate = engagementRate ?? estimateEngagement(followers);
  const engagementMultiplier = getEngagementMultiplier(effectiveEngagementRate, followers);
  const contentTypeMultiplier = CONTENT_TYPE_MULTIPLIERS[contentType] || 1.0;
  const deliverableMultiplier = getDeliverableMultiplier(
    deliverables.map(d => ({ type: d.type, quantity: d.quantity }))
  );
  const industryMultiplier      = getIndustryMultiplier(industry);
  const geographyMultiplier     = getGeographyMultiplier(geography);
  const durationMultiplier      = getDurationMultiplier(campaignDuration);
  const usageRightsMultiplier   = getUsageRightsMultiplier(usageRights);
  const exclusivityMultiplier   = getExclusivityMultiplier(exclusivity);
  const rushMultiplier          = getRushMultiplier(rushJob);
  const revisionMultiplier      = getRevisionMultiplier(revisions);
  const platformAdjustment      = PLATFORM_MULTIPLIERS[platform] || 1.0;

  const subtotal = basePrice *
    engagementMultiplier * contentTypeMultiplier * deliverableMultiplier *
    industryMultiplier * geographyMultiplier * durationMultiplier *
    usageRightsMultiplier * exclusivityMultiplier * rushMultiplier *
    revisionMultiplier * platformAdjustment;

  const finalPrice = Math.round(subtotal / 10) * 10;
  const priceRange = {
    min: Math.round(finalPrice * 0.85 / 10) * 10,
    max: Math.round(finalPrice * 1.15 / 10) * 10,
  };

  return { basePrice, engagementMultiplier, contentTypeMultiplier,
    deliverableMultiplier, industryMultiplier, geographyMultiplier,
    durationMultiplier, usageRightsMultiplier, exclusivityMultiplier,
    rushMultiplier, revisionMultiplier, platformAdjustment, subtotal,
    finalPrice, priceRange, currency, tier,
    estimatedEngagement: effectiveEngagementRate };
}
Strategic Decisions

Five decisions that shaped the build

Why a deterministic algorithm instead of just using OpenAI?

Financial decisions require auditable math. The deterministic engine shows exactly how each factor contributes to the final price. OpenAI is used only for narrative explanation—never for the actual calculation. This creates trust: creators can defend their rates, and brands can verify fairness.

High Impact
Why influencer pricing instead of freelance developer pricing?

The README positions Ratewise as a freelance rate calculator, but the actual pricing engine and schemas are built for social media creators (platforms, followers, engagement, content types). The OpenAI layer handles freelance rates as a secondary use case. The creator economy has more standardized variables (followers, engagement, platform) making it better suited for algorithmic pricing.

High Impact
Why Supabase Auth over Clerk (which the API route imports)?

The project uses Supabase Auth throughout—middleware, schema, and client. However, app/api/calculate/route.ts imports @clerk/nextjs/server, which is not in package.json. This appears to be leftover code from an earlier auth approach. The working auth flow is Supabase.

Medium Impact
Why fixed exchange rates instead of a live API?

The currency conversion uses hardcoded rates (USD 1.0, EUR 0.92, GBP 0.79, CAD 1.36, AUD 1.52). For a pricing tool, approximate conversion is acceptable—creators typically quote in their primary currency. A live API would add cost and latency for marginal accuracy gain.

Low Impact
Why watermark free users' rate cards?

The rate card preview component shows a watermark for non-paid users. This is a classic freemium conversion mechanic—users can see the full quality of the output but need to upgrade to remove branding.

Medium Impact

Reflection

What worked, what I would change, what I learned

What worked

  • The deterministic pricing engine is the strongest feature—transparent, fast, and entirely client-computable if needed
  • Stripe integration is production-grade with comprehensive webhook handling and subscription state sync
  • Database schema is well-designed with RLS, indexes, triggers, and proper normalization
  • Zod schemas provide end-to-end type safety from API to database

What I would change

  • Fix the frontend/API mismatch: the RateCalculator React component collects freelance data but sends to /api/calculate which expects influencer data
  • Add actual test files—the project has Jest and Playwright dependencies but zero tests
  • Complete the market scraper or remove Puppeteer dependency until it is implemented
  • Remove the @clerk/nextjs import from the calculate API route (dependency not in package.json)
  • Write the documentation files referenced in README

Lessons

  • A deterministic algorithm paired with an AI narrator is more trustworthy than AI alone for financial decisions
  • Freemium conversion mechanics (watermarks, calculation quotas) need to be visible early in the user journey
  • README promises should match code reality—claiming Jest tests and live scraping when neither exists damages credibility
